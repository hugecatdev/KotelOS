# Замеры: стоит ли многоядерность (SMP) в v86

Два вопроса, 2026-11-07: (1) сколько вообще выиграли бы несколько ядер в наших
сценариях и (2) сколько стоит то, без чего SMP на ARM-телефонах не будет
правильным, - упорядоченные (атомарные) обращения JIT к памяти гостя.

## 1. Потолок выигрыша: `split.py` + `ktop`

`ktop` (`ktop.c`, i386 static) - сэмплер внутри однопроцессорного гостя. Раз в
50 мс читает `/proc/stat`: занятые тики шага (без своих) кладёт в корзину по
`procs_running` - сколько ДРУГИХ задач готовы работать. Раз в 500 мс - время
каждого потока из `/proc/*/task/*/stat`. Выходит сам, когда гость 2 с почти без
дела, и пишет `KTOP-DONE` в `/dev/console` (страница видит это без нагрузки на
гостя - опросы через `exec()` сами были работой и портили замер).

Оценка на N ядрах (HZ=100, учёт по тикам):

- по очереди готовых: `T_N = простой + Σ тики_k / min(k, N)` - реалистичная, но
  занижает конвейеры (на одном ядре `seq` заполняет канал и засыпает, k=1);
- сверху: `T_N = простой + max(занято / N, самый большой поток)` - не знает о
  зависимостях, завышает скрипты и запрос-ответ X.

```sh
i686-linux-musl-gcc -O2 -static -s -o tests/smp/ktop tests/smp/ktop.c
python3 tests/smp/split.py dwm      # startx, st-seq, xcalc, feh, gzip, pkg-add
python3 tests/smp/split.py python   # idle, mpldemo
python3 tests/smp/split.py qt       # pyqt-studio (Designer + форма PyQt5)
```

Бандлы - готовые `site/*/index.html` (`release.py`), Chromium headless 800x600,
v86 из main 8f0d31d.

| сценарий | 1 ядро, с | 2 ядра | 4 ядра | кто работает |
|---|---|---|---|---|
| `startx` (dwm + 2 st) | 5.8 | 1.44x (до 1.99) | 1.63x | Xorg 24%, st 17+16%, dwm 10%, xkbcomp 9% |
| st печатает `seq 1 20000` | 3.3 | 1.72x (до 2.00) | 2.07x | st 35%, Xorg 29%, seq 19% |
| старт xcalc | 0.8 | 1.06x | 1.08x | Xorg 42%, xcalc 36% - запрос-ответ |
| feh, картинка 640x480 | 0.4 | 1.21x | 1.21x | Xorg 36%, feh 26% |
| `seq \| gzip \| wc` | 4.3 | 1.23x (до 1.89) | 1.26x | seq 53%, gzip 32% |
| `kt pkg add python3` | 8.9 | 1.18x | 1.20x | xz, tar, awk - по очереди |
| старт IDLE | 7.0 | 1.10x | 1.10x | два python3: 52% и 33%, друг за другом |
| старт mpldemo (matplotlib) | 5.6 | 1.13x | 1.14x | один python3 91% |
| старт pyqt-studio | 42.0 | 1.06x | 1.07x | Qt Designer 79% одним потоком, python3 16% |

Сырые числа: `split.py ... --json`.

## 2. Цена атомарных обращений: `v86-atomic-probe.patch`

Патч на дерево `scripts/build-v86.sh` (обработанная копия `.cache/v86-REV`,
`patch -p1`, потом `make build/v86.wasm`; libv86.js не меняется). Все 20 обращений
быстрого пути JIT к памяти гостя (`gen_safe_read`, `gen_safe_write`,
`gen_safe_read_write` в `codegen.rs`) идут по `SMP_PROBE`:

| `SMP_PROBE` | что | x86, к v86 |
|---|---|---|
| 0 | как в v86 | 1.000 (копия базы - 1.005) |
| 1 | ветка по выравниванию на каждом обращении, обычные операции, невыровненные - `atomic.fence` | 1.124 |
| 2 | то же, выровненные - `i32/i64.atomic.load/store` (8/16 бит тоже) | 1.164 |
| 3 | атомики без лишней ветки: выравнивание влито в проверку TLB вместо «не через страницу» (выровненное до 8 байт страницу не пересекает), у быстрого и медленного пути свои хвосты, невыровненные - медленным путём с `fence`; чтение-изменение-запись - как 2 | **1.068** |
| 4 | раскладка 3, но обычные операции и прежнее условие | 1.025 |

Среднее геометрическое процессора основного потока по 12 нагрузкам `tests/bench.py`,
медиана из 4 кругов `pbench.py` (2026-11-07, Chromium headless, нагрузка хоста 3-22).
Цена правильного порядка памяти на x86 - около 7% (3 против 0), из них ~4% - сами
атомики и медленный путь невыровненных (3 против 4). Наивная ветка на каждом
обращении (1, 2) стоит вдвое больше.

Как мерить:

- `pbench.py БАЗА ВАРИАНТ...` - все варианты одновременно, каждый в своём Chromium,
  нагрузки стартуют разом. `tests/bench.py` (по очереди) на общем хосте давал шум
  ±12% даже у базы и однажды показал вариант 3 как 0.912, а в другой раз 1.110;
- `jitcheck.py ПАПКА` - все ли модули JIT приняты и есть ли в них атомики: в
  release-сборке v86 отказ `WebAssembly.instantiate` молча оставляет интерпретатор;
- `atomics-micro.js` (node) - цена атомиков в V8 без v86: запись ×10.8 (`xchg`, 4.15
  против 0.38 нс), чтение ×1.35; на обычной и shared памяти одинаково - V8 их не
  упрощает, поэтому shared для замера не нужна.

На ARM атомарные чтение и запись - `ldar`/`stlr`, их цена другая, и число с x86 про
телефон не говорит. Для телефона - `phone.html`: `phone-kit.py ПАПКА vendor/v86
СБОРКА_3` кладёт рядом base.html, atomic.html и index.html; раздать по http
(`python3 -m http.server 8090 --bind 0.0.0.0 -d ПАПКА`) и открыть на телефоне,
вкладка на виду, 3 круга (~15 мин), в конце - таблица и сырые числа для копирования.

Не измерено: per-CPU база регистров (сейчас абсолютные адреса 64..~1000 в коде JIT),
сброс кода между потоками при записи в страницу с кодом, атомарные RMW для `lock`.
