# Бандлы и сохранения

## Бандлы

Машина для браузера - всегда один html-файл (бандл): v86, BIOS, xterm.js,
ядро, rootfs с нужными пакетами и, если надо, готовый снимок запущенной
машины. Работает и с сайта, и двойным кликом через `file://` без сети.
Остальные пакеты `kt pkg add` берёт из общего репозитория (`--repo`).

```sh
./build.sh                                   # образ -> images/, пакеты -> site/repo/
python3 bundle.py --bare                     # site/index.html: только busybox и kt, 3.1 МБ
python3 bundle.py --snap -n standard -o site/standard/index.html
python3 bundle.py -o numpy.html -n numpy --mem 256 python3 pip python-numpy --run python3
python3 bundle.py -o mini.html -n mini fun --snap
python3 bundle.py -o java.html -n java --mem 384 --file bundles/java/Hello.java \
  --cmd "javac Hello.java && java Hello" jdk8
./release.py                                 # все бандлы сайта из bundles/ в site/, см. «Бандлы сайта»
```

| ключ | что делает |
|---|---|
| `пакеты...` | что поставить в rootfs (по умолчанию fun nano htop minipython lua5.4 pyzygote curl wget python-requests pack notify kt-share ai examples-python examples-lua kt-ttyd tk-desktop tk-term) |
| `--bare` | без пакетов: только busybox и `kt`, остальное - `kt pkg add` из репозитория |
| `-o файл` | куда (по умолчанию `site/index.html`); чужой не-бандл не перезаписывает |
| `-n имя` | имя бандла: своё сохранение у каждого имени, видно в `kt info` и заголовке вкладки |
| `--repo url` | откуда `kt pkg add` качает пакеты (по умолчанию `/repo`; для файла, который раздаёшь отдельно, - полный `https://<сайт>/repo`, нужен CORS) |
| `--snap` | загрузить машину при сборке (headless Chromium) и положить её снимок: файл открывается сразу в готовую машину, ~2 с вместо ~5 |
| `--run CMD` | перед снимком набрать команду (можно несколько, подразумевает `--snap`): `--run python3` - бандл открывается в уже загруженный питон, `--run startx` - сразу в X на экране (снимок помнит экран и размер X) |
| `--prep CMD` | перед снимком выполнить команду мимо терминала (можно несколько, подразумевает `--snap`): прогреть кэши, экран остаётся чистым; ненулевой код останавливает сборку |
| `--keep-boot` | оставить в файле ядро рядом со снимком, тогда работает `kt reset -b` |
| `--mem МБ` | память машины по умолчанию (`boot.mem`), иначе 128: питоновскому бандлу с numpy нужно 256 |
| `--worker` | `boot.worker` по умолчанию on: v86 в Web Worker, страница (терминал, экран) в своём потоке |
| `--vga [МБ]` | экран (`boot.vga`): видеопамять 4, 8 или 16 МБ (без числа - 8), `/dev/fb0`; это память вкладки, см. [screen.md](screen.md). С ним и 3D для программ OpenGL (virtio-gpu, `vendor/virgl`, +0.4 МБ к бандлу; память - только когда такая программа запущена) |
| `--no-3d` | бандл с `--vga` без 3D: OpenGL только программный (softpipe) |
| `--phone-scale CSS` | экран на телефоне при `screen.scale auto`: точек страницы на точку X (иначе 1), целое число пикселей экрана берётся меньшее; на ПК не действует (бандл `qt` - 0.75, иначе окна Designer не влезают) |
| `--save-timer МИН` | `save.timer` этого бандла по умолчанию: сохранять машину каждые N минут (иначе 0 - только при сворачивании вкладки) |
| `--cmd CMD` | команда при загрузке по умолчанию (`boot.cmd`): выполняется в новой машине, не после восстановления сохранения |
| `--embed` | для своего сайта через `embed.js`: внутри iframe страница - только окна tk поверх сайта, без терминала; открытый сам по себе бандл - обычный. Без ключа этого кода на странице нет, см. [api.md](api.md) «Окна поверх сайта» |
| `--file ФАЙЛ[:ПУТЬ]` | положить свой файл в образ (по умолчанию в `/root/`), можно несколько; папку - её содержимое в ПУТЬ с правами (`--file bundles/qt/fs:/`). Отдельный шелл-скрипт (`#!/bin/sh`, например `~/.xinitrc`) ложится сжатым, как скрипты пакетов: без комментариев, пустых строк и отступов; папка - как есть. Это данные бандла, а не пакет: в репозитории и `kt pkg` их нет |
| `--version ИМЯ` | необязательная метка бандла, строка `version:` в `kt info` |

Пакеты, которых нет в репозитории, берутся из Alpine (по `alpine.txt.gz`,
`.apk` качаются на хосте с dl-cdn): `python3 bundle.py openjdk8-jdk` соберёт
машину с полным JDK из Alpine. Их триггеры (`.trigger`, например у
`java-common` - ссылки `java`/`javac` в `/usr/bin`) выполняются при первом
входе, как post-install.

Питоновский бандл (`bundles/python.txt`, 43 МБ, 76 пакетов): `python3` с `pip`,
`sqlite3` и `curses`, numpy, tkinter, IDLE, turtle и matplotlib с примерами
(`idle`, `turtledemo`, `mpldemo`), 384 МБ памяти. Со снимком: файлы пакетов
(79 МБ) и `pyzygote` с уже загруженным matplotlib в снимке сжимаются до 31.5 МБ,
машина открывается за ~2 с, кэш шрифтов matplotlib построен при сборке. Вкладка
(`tests/mem.py`) держит ~285 МБ, пик при загрузке ~720 (до своих numpy и openblas
и чистки пакетов было 48 МБ файла, ~320 МБ и ~850 на пике); похожий набор без снимка
(matplotlib и turtle с ядра, 38 МБ) грузился 5.5 с и держал 593 МБ, пик 826.

Java-бандл (пример выше, 76 МБ): без снимка, при загрузке компилирует и
запускает `bundles/java/Hello.java` (загрузка ~11 с, `javac` ~15 с). Вес - это
сам JDK: `rt.jar` 35 МБ, `libjvm.so` 12 МБ, `tools.jar` 9 МБ уже сжаты внутри;
снимок добавлял лишь RAM с теми же файлами. Полный openjdk8 из Alpine давал
100 МБ.

Со снимком ядро и initrd по умолчанию из файла убираются: машина всегда
стартует из снимка, `kt reset` возвращает к нему же. Снимок крупнее ядра с
initrd: файлы пакетов в нём лежат распакованными (стандартный набор - 10 МБ
файл против 9.4, с python3 - 13 против 11.4). Сборка со снимком ждёт, пока гость
успокоится: процессор занят меньше 10% (`/proc/stat` внутри гостя) и 1.5 с
нет вывода; `--timeout` - сколько ждать каждую `--run`.

Публикация: бандлы кладутся куда угодно (`/`, `/python/`, ...), репозиторий
один - содержимое `site/repo/` в `/repo/`. initrd внутри сжат `zstd -19` и
отдаётся v86 как blob-URL `...#initrd.zst` (распаковывает встроенный в v86 zstd),
снимок - тоже zstd, wasm и BIOS - gzip через `DecompressionStream`, скрипт
страницы - terser (`npx terser`, без него остаётся как есть). Двоичные части
(wasm, BIOS, ядро, initrd, снимок) лежат в html отдельными
`<script type="application/base64" id="kt-...">`, а не строками в js: для
браузера это одна копия текста, страница забирает байты и убирает тег, см.
«Память» в [internals.md](internals.md). Своих шрифтов нет:
терминал и кнопки - системный моноширинный, как в Termux. Пакеты ставятся прямо
в initrd вместе с записями `kt pkg`, так что `kt pkg rm` работает; их
post-install (приветствие `fun`) выполняется при первом логине (в бандле со
снимком - ещё при сборке). Шаблон страницы - `page.html`, сам по себе он не
грузится.

## Бандлы сайта

На сайте лежат семь бандлов, все со снимком: `python` (полный CPython с pip и numpy, tkinter,
IDLE, turtle и matplotlib с примерами, рабочий стол, терминал и `ai`; 384 МБ памяти),
`standard` (пакеты по умолчанию, с ними и рабочий стол `tk-desktop` и терминал в окне `tk-term`,
см. [Окна](gui.md)), `micro` (базовые инструменты: nano, htop, tmux, curl, wget, pack, notify),
`xorg` (экран с видеопамятью 8 МБ, 256 МБ памяти, X без OpenGL: при открытии сразу `startx` -
twm, xterm, xcalc и xeyes, см. [Экран](screen.md)), `dwm` (максимальный: тот же экран, `startx`
при открытии - dwm с обоями и часами в панели, st с neofetch, xclock, xcalc, xeyes, шахматы
xboard с gnuchess, OpenGL с `mesa-utils` и `mesa-demos`), `sqlite` (DB Browser for SQLite под dwm,
открывается сразу в X с демо-базой `~/packages.db` - пакеты репозитория и их зависимости) и `qt`
(`dwm-studio`, Qt Designer и PyQt5, 384 МБ памяти: открывается сразу в X - слева (на экране стоя -
сверху) Designer с формой, рядом она же живая с кодом, `pyqt-studio`; сохраняется каждые 2
минуты). У бандлов с экраном v86 в Web Worker (`--worker`): страница и экран не ждут эмуляцию,
по-старому - `kt cfg boot.worker off`.

`xorg` и `dwm` поднимают X командой при открытии (`--cmd startx`), а не из снимка (`--run startx`):
снимок помнит X того размера, какой был у окна сборки, и хотя X потом переходит на размер
страницы, twm окна не переставляет, а обои и вывод neofetch остаются прежними - на телефоне окна
уезжали за край. `sqlite` и `qt` снимаются с запущенным X (`--run startx`): их программы
открываются полминуты, а dwm сам раскладывает окна под новый размер. Снимок бандла с `--cmd`
`bundle.py` снимает без `boot.cmd`, иначе команда выполнилась бы ещё при сборке.

`release.py` собирает бандлы с `--repo ../repo` (если в описании нет своего `--repo`): бандл
лежит в `ИМЯ/`, репозиторий - рядом, и такой адрес годится и для корня сайта, и для
`https://<пользователь>.github.io/<репозиторий>/`, где `/repo` указывал бы мимо.
Что в каком - в `bundles/ИМЯ.txt`: аргументы `bundle.py`, как в командной
строке, `#` - комментарий. Новый файл там - новый бандл.

```sh
./release.py                # собрать все бандлы в site/ИМЯ/index.html
./release.py micro python   # только эти
./release.py --build        # сначала ./build.sh, потом бандлы
```

Бандлы собираются из текущих `images/` и `site/repo`. Старый
`site/ИМЯ/index.html` заменяется только готовым новым, так что сайт можно
раздавать прямо во время сборки. Побайтно бандл не повторяется: снимок - это
живая машина, а terser берётся через `npx`.

## Сохранения и снимки

Два уровня. Сохранение - одно на имя бандла (`-n`), из него страница
загружается. Снимки - именные копии, общие для всех бандлов сайта, сами по себе
не загружаются. Без сохранения бандл стартует со своего встроенного снимка, а
если его нет - с ядра.

| команда | что делает |
|---|---|
| `kt save` | машина -> сохранение (так же пишет автосохранение) |
| `kt load` | перезагрузить страницу из сохранения, всё несохранённое пропадает |
| `kt save work` | машина -> снимок `work` |
| `kt load work` | снимок `work` -> сохранение этого бандла, дальше как `kt load` |
| `kt snap` | список снимков |
| `kt snap rm work` | удалить снимок |
| `kt reset` | удалить сохранение этого бандла и начать заново: со встроенного снимка, а без него - с ядра; снимки и другие бандлы не трогает |
| `kt reset -b` | то же, но загрузиться с ядра, даже если есть встроенный снимок (если ядро оставлено `--keep-boot`) |
| `kt export [work]`, `kt import` | сохранение или снимок в файл, файл -> сохранение |

`kt load`, `kt reset` и `kt snap rm` спрашивают `[y/N]`, `-y` - без вопроса
(`kt reset -yb`).

Снимок - это вся машина вместе с запущенными процессами: после `kt load work`
продолжает выполняться и та командная строка, из которой звали `kt save work`.
При `kt load` и `kt reset` автосохранение не срабатывает. `kt load` в первые
5 секунд после восстановления пропускается - иначе `kt save; kt load -y` в одной
строке перезагружал бы страницу по кругу.

## Машина файлом: kt share

Пакет `kt-share`: `kt share` или кнопка собирает html - ту же страницу с тем
же v86, только встроенный снимок - машина как сейчас. Кнопка - полупрозрачный
значок у правого края внизу (на телефоне - над рядом клавиш), поверх терминала
и экрана X; пока собирается файл, он мигает.
Файл отправляют другому, он открывает его в браузере, правит и своим
`kt share` шлёт обратно. Снимок с эмулятором не разойдётся: файл везёт свой
v86 и BIOS, а не только снимок, как `kt export`.

| команда | что делает |
|---|---|
| `kt share` | эта машина новой ревизией, файл `<имя>.html` (имя - от бандла, потом - от проекта) |
| `kt share имя` | новая машина-проект `имя` (до 24 знаков): у получателя отдельно от прежних |

Как не путаются сохранения:

- У копии своё имя бандла - id проекта, `имя-xxxxxx`, и свой слот сохранения:
  её не перекроет ни сохранение обычного бандла, ни другой проект с тем же
  именем. Все ревизии проекта ложатся в этот один слот. Проект записан в самой
  машине (`/var/lib/kt/share`) и уезжает со снимком, так что следующий
  `kt share` - та же машина, а не новая.
- У каждого `kt share` новая ревизия. Сохранение помнит ревизии, от которых
  пошла машина. Файл, от которого твоё сохранение пошло, продолжает его (в
  том числе более старая ревизия). Новая чужая ревизия побеждает, а твоё
  сохранение уходит в снимок с именем проекта (`kt load имя-xxxxxx` вернёт), и
  страница об этом пишет. Снимок один на проект: следующий такой раз его
  перезаписывает.
- Две живые машины не сливаются: это эстафета, а не совместная правка.

Файл собирается из самой страницы: части бандла она после загрузки удаляет из
DOM, поэтому при открытии, пока DOM нетронут, берёт свой исходник без снимка и
ядра (~2 МБ в хранилище браузера, `kt.source`). Так копия собирается и из
`file://`, и без сети, и сайт заново не качается. Берёт его страница, только
где kt-share есть: бандл собран с ним (`bundle.py` ставит `share` в
`KT_BUNDLE`, у копий он тоже) или в прошлый раз отметился хук пакета
(`kt.keepSource`); отметку страница снимает при каждой готовности машины, так
после `kt pkg rm kt-share` исходник со следующего открытия не берётся. Если
пакет поставили в уже открытой странице, `kt share` попросит `kt save` и
обновить её. Снимок в файле - gzip (`CompressionStream`, zstd браузер не пишет), поэтому копия
больше бандла с сайта примерно на треть снимка. Замеры 2026-11-08 на бандле
python (headless Chromium на ПК): копия 58 МБ против 44; `kt share` - 5.5 с
до файла, пик вкладки 527-543 МБ против 452-516 у `kt save` (файл
собирается в хранилище браузера, снимок кодируется в base64 кусками по 48 КБ:
большие куски копились до полной сборки мусора, пик был до 655 МБ);
открыть копию - как своё сохранение, пик ~500-530 МБ против ~470 у бандла
со zstd; исходник при открытии - в пределах шума (пик загрузки 449-467 МБ
против 465-475 без него). Адрес репозитория пакетов в
копии - полный, `boot.cmd` и `--cmd` в ней не выполняются. Не переезжают
настройки страницы (`kt cfg`), папки `kt sync` и 3D-контексты.

## Публикация

Собрать бандлы (`./release.py`) и загрузить содержимое `site/`: бандлы
(`python/`, `standard/` и другие, куда собраны) и `repo/` (качается только то, что ставят).
Больше ничего не нужно: всё остальное внутри бандлов.

GitHub Pages - `scripts/pages.sh [REMOTE]` (по умолчанию `origin`): ветка `gh-pages` каждый раз
с нуля, без истории (иначе каждая выкладка копила бы в репозитории сотни МБ), и `push --force`.
В ветке - сборки из `bundles/*.txt`, `repo/`, `index.html` с переходом на `python/` (другая -
`ROOT=dwm scripts/pages.sh`) и `.nojekyll`. `scripts/pages.sh -n` только собирает `build/pages`.
На GitHub один раз: Settings -> Pages -> Deploy from a branch -> `gh-pages`, `/ (root)`. Пределы
GitHub: файл до 100 МБ (от 50 - предупреждение при push), сайт до 1 ГБ.
